# 一万个网站、一万种 DOM：异构采集系统的设计与落地

给十几个网站写解析器，轻松愉快；站点数量涨到几千上万，域名不同、DOM 结构全不一样，事情就变味了。写规则写到手软，规则失效修到手软，最后发现大部分时间不是在写爬虫，而是在给已有爬虫「救火」。

两件事：**整条采集链路怎么跑起来**，以及更关键的——**面对一万种不同的 DOM，解析层到底该怎么设计**。

先说结论：这个问题没有「一套通用解析器」的银弹，正确解法是**分层策略 + 规则资产化 + 自动降级**。把站点按价值分层，让不同层级用不同成本的解析方式，再靠监控闭环把规则失效的损耗控制在可维护范围内。

## 一、整体流程：八段流水线

异构问题主要出在解析环节，但解析不是孤立存在的，前后环节的设计会直接影响解析层的压力。完整链路长这样：

```
种子库 → 调度 → 抓取 → 渲染判定 → 抽取 → 校验清洗 → 存储 → 监控回流
```

逐段说清楚每段的关键决策：

**1. 站点注册与种子库。** 所有站点信息入库，不写死在代码里。每个站点一条记录：域名、目标 Schema（要抽哪些字段）、解析规则版本、渲染策略、抓取频率、合规标记。这一条决定了后面所有环节能不能配置化运转。

**2. 调度 Frontier。** 用 Redis 或 Kafka 做分布式队列，核心设计是**按域名分桶限速**——同一站点的请求串行化并加上间隔，不同站点之间充分并行。再叠加布隆过滤器做 URL 去重，按页面变更频率做增量调度。

**3. 抓取 Fetch。** Scrapy 集群加代理池，UA 和指纹轮换，失败重试带熔断。能走纯 HTTP 的绝不渲染，这是成本最低的路径。

**4. 渲染判定。** 先走 HTTP，检测到主体内容由 JS 注入（比如 body 里几乎是空的、只有 bundle 入口）再升级到 Playwright 无头浏览器。经验上只有两三成站点需要真渲染，这一步能省下大量浏览器资源。反爬对抗按站点分级：换 UA、换 IP、降速、接验证码服务，逐级升级，顺便给每个站记一份「对抗成本画像」，后面做解析分层时用得上。

**5. 抽取。** 本文的主角，下一章展开。

**6. 校验与清洗。** 每条抽取结果过 Schema 校验：必填字段是否存在、类型对不对、时间格式能不能解析。字段非空率顺便作为站点级健康指标沉淀下来。内容去重用 SimHash 或 MinHash。

**7. 存储。** 双层存储：原始 HTML 进对象存储（WARC 格式），结构化结果进 PG / ClickHouse / ES。存原始 HTML 不是浪费空间，它保证规则失效后可以**离线重放、重新抽取**，不用重新抓一遍，这是省大钱的设计。

**8. 监控与回流闭环。** 按站点监控抓取成功率和抽取成功率，跌破阈值触发告警，定位是抓取挂了还是模板改版了，修完规则重新调度。这条回路决定了系统是越跑越稳，还是跑一个月就烂尾。

## 二、解析一万种 DOM：核心思路是分层

先算一笔账。假设人工给一个站点写规则加调试要 1 小时，一万个站就是一万小时，五个工程师干一年。而且 DOM 改版是常态，规则维护是持续成本。所以「给每个站写一套解析器」这条路从第一天就走不通。

反过来，「一套通用算法通吃所有站」也走不通——通用正文抽取对结构规整的文章页能有八九成准确率，但对电商详情页、列表页、论坛帖这种字段密集的目标，准确率会直接垮掉。

实际可行的方案是把站点分成三层，匹配四级解析策略：

### 2.1 站点分层：先决定谁值得花成本

按业务价值和对抗成本，把站点分成：

- **头部站点**（约占 5%）：数据价值高，值得投入人工定制规则，要求 99% 级别的准确率；
- **腰部站点**（约占 30–40%）：价值中等，靠模板聚类摊薄规则成本；
- **长尾站点**（剩下一大半）：价值低或形状不规整，用零配置的通用算法和 LLM 兜底。

分层的本质是**把有限的人工预算花在回报率最高的站点上**。

### 2.2 L1：配置化规则，而不是硬编码规则

这种方案我之前采集舆论信息的时候，搞过

头部站点写 XPath / CSS 选择器没问题，问题是别让规则活在代码里。规则入库、版本化，运营就能接管大部分维护工作：

```yaml
site_id: news-0001
domain: example-news.com
parser: rule
rule_version: 12
fields:
  title:    //h1[contains(@class,"article-title")]/text()
  pub_time: //time/@datetime
  author:   //span[@class="author"]/text()
  content:  //div[@id="article-body"]
pagination:
  list_url: "https://example-news.com/list?page={page}"
  item_link: //a[@class="title"]/@href
```

再进一步，做一个可视化标注工具：运营在页面上点选标题、时间、正文，工具自动生成候选选择器并回显抽取预览。这一步把规则生产的单位成本从「工程师一小时」压到「运营十分钟」，头部站点的覆盖速度直接翻倍。

### 2.3 L2：模板聚类——把 O(n) 压成 O(k)

这是规模化最关键的一步。一万个站点听起来是一万种 DOM，实际上大量站点共用同一个 CMS（WordPress 占了内容站的大头）、同一套建站模板，或者干脆是同一个站群换皮。**同模板的站点，一条规则可以通吃。**

聚类的技术抓手有三个：

**DOM 骨架哈希。** 把 DOM 树剥掉所有属性、文本，只保留标签结构，取前几层算哈希：

```python
from lxml import html
import hashlib

def dom_skeleton(html_bytes: bytes, depth: int = 6) -> str:
    doc = html.fromstring(html_bytes)

    def walk(el, d):
        if d > depth or not isinstance(el.tag, str):
            return ""
        children = "".join(sorted(walk(c, d + 1) for c in el))
        return f"<{el.tag}>{children}</>" if children else f"<{el.tag}>"

    return hashlib.md5(walk(doc, 0).encode()).hexdigest()
```

骨架哈希相同的页面，大概率出自同一个模板。新站点入库时先算哈希，命中已有聚类就直接复用该群的规则，零人工接入。

**CMS 指纹识别。** Generator meta 标签、标志性路径（`/wp-content/`）、cookie 名、静态资源命名，都能快速识别 WordPress、Discuz、Shopify 这类常见系统，每个 CMS 准备一套预置规则模板。

**URL 模式归并。** 同一站点内，列表页、详情页、分页的 URL 模式不同，解析规则也不同。按 URL 正则把页面分成几类，每类各自聚类。

腰部站点走完这层，实际需要人工介入的规则数量往往只剩几百条，而不是几千条。

### 2.4 L3：通用正文抽取，长尾的免费午餐

对于资讯、博客、文档这类「一段主文」的页面，通用抽取算法不需要任何站点配置。主流实现（readability、trafilatura、newspaper4k）的核心思路都是**文本密度分析**：

- 统计每个 DOM 节点的文本长度、链接文本占比、标点密度；
- 正文区域的特征是文本长、链接占比低、逗号句号密度高；
- 导航、侧栏、页脚则是链接密集、正文稀疏。

trafilatura 在这之上还叠了站点结构先验和元数据提取（标题、时间、作者），对文章型页面的准确率能到 85–90%。代价是它几乎只能抽「正文」这一个字段，对字段密集的目标页面无能为力——所以它只负责长尾里形状合适的那部分。

### 2.5 L4：LLM 兜底，给高价值长尾一个出路

总有一批站点：结构不规则、模板聚类聚不上、通用算法抽不准，但数据又确实有价值。大模型给了一个新选项——把清洗过的 DOM 丢给它，按 Schema 约束输出结构化 JSON。

直接喂整页 HTML 不可行，token 成本会爆炸。关键是先做 DOM 瘦身：

```python
def slim_dom(doc, keep_attrs=("href", "src", "datetime")) -> str:
    """剥掉 script/style/注释和无关属性，只留可见文本骨架。"""
    for xp in ("//script", "//style", "//noscript", "//svg", "//comment()"):
        for el in doc.xpath(xp):
            el.getparent().remove(el)
    for el in doc.iter():
        if isinstance(el.tag, str):
            keep = {k: v for k, v in el.attrib.items() if k in keep_attrs}
            el.attrib.clear()
            el.attrib.update(keep)
    return html.tostring(doc, encoding="unicode", method="html")
```

瘦身后的 DOM 通常只剩原体积的 10–20%。再配合两件事控制质量和成本：

- **Schema 约束输出**：用 JSON Schema 或 function calling 强制模型按字段输出，回来还要过和规则解析一样的校验器，不合格就重试或放弃；
- **成本闸门**：LLM 调用按页面计费，只放给「前面三级都失败且标记为高价值」的页面，别让它成为默认路径。抽出的结果人工抽检确认后，可以反过来沉淀成 L1/L2 规则——LLM 顺手变成了规则生产工具。

### 2.6 把四级策略串成一条降级链

四个层级不是二选一，而是一条逐级降级的路由链：

```python
PARSERS = [RuleParser, TemplateParser, ReadabilityParser, LLMParser]  # L1 -> L4

def extract(page, site):
    for cls in PARSERS:
        if cls.level < site.preferred_level:
            continue
        result = cls(site).extract(page)
        if result and validate(result, site.schema):
            if cls.level > site.preferred_level:
                alert.parser_downgraded(site, cls.level)  # 降级说明规则可能失效了
            return result
    alert.extract_failed(site, page.url)
    return None
```

每个站点有期望层级，实际运行时可以往下降级保命，但降级事件本身要进告警——它往往就是模板改版的第一个信号。

## 三、让系统活过三个月：模板漂移监控

写爬虫系统最常见的死法不是没爬下来，而是站点改版后规则悄悄失效，几周后才发现数据全是空的。

前面埋的两个设计在这里闭环了：

1. **DOM 骨架哈希的另一个用途是漂移检测。** 定时对站点首页和样本详情页重算骨架哈希，哈希变了、聚类对不上了，基本就是改版了，触发规则复核工单；
2. **抽取成功率和字段非空率是按站点监控的。** 非空率从 98% 跌到 40%，不等用户报障，告警先响；
3. 修复后的规则发新版本入库，同时用存储的原始 HTML **离线重放验证**新规则，确认无误再放量重新调度。

聚类、降级、漂移检测、重放验证串起来，系统的维护成本才是收敛的。没有这个闭环，一万个站点就是一万颗定时炸弹。

## 四、几个容易踩的坑

- **渲染判定别偷懒。** 全量上无头浏览器，资源成本翻十倍不止；全靠 HTTP，一批 SPA 站点抓回来是空壳。判定逻辑要按站点记录，别每次现测。
- **去重要分两层。** URL 级去重靠前调度，内容级去重靠后 SimHash，只做一层迟早被改参数刷量的站点教育。
- **原始 HTML 一定要存。** 第一次觉得浪费存储，第一次模板改版后你会感谢这个决定。
- **合规是前置条件不是事后补救。** robots.txt、站点服务条款、速率礼仪、版权和个人信息边界，入库时就要标记，而不是被告了之后才查。

## 五、落地节奏

不要试图第一天就覆盖一万个站。推荐的推进顺序：

1. **MVP 阶段**：Scrapy + Redis 队列 + 配置化规则引擎，先拿 100 个种子站跑通全链路，重点验证监控回流闭环是否真的闭得上；
2. **规模化阶段**：补 Playwright 渲染池和代理池，上线模板聚类，扩到三千站，验证聚类命中率；
3. **长尾覆盖阶段**：接入通用抽取和 LLM 兜底，补齐全量，同时把规则维护移交给运营，工程师回到系统本身。

## 结语

一万个异构网站的采集，表面上是爬虫技术问题，实质是一个**成本分配问题**：人工规则给头部，模板聚类给腰部，通用算法和 LLM 给长尾，再用监控闭环把规则失效的损耗兜住。单点技术——Scrapy、Playwright、trafilatura、大模型——没有一样是稀缺的，稀缺的是把它们按正确的层级组织起来的那套工程设计。
